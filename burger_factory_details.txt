1. EXECUTIVE PROJECT OVERVIEW
================================================================================
"The Burger Factory" is a premium, modern web application designed for an iconic
gourmet burger brand originated in Anjuna, Goa, and expanded across 7 locations
(Anjuna, Morjim, Vagator, Nerul, Dona Paula, Panaji, and New Delhi).

The project solves the restaurant's #1 operational challenge: Long waiting lines
and table turn management during peak hours. It provides:
1. Customer Experience (index.html):
   - Immersive brand presentation with gourmet visuals, particle animations,
     animated stats counters, and interactive story/menu/locations/reviews sections.
   - Real-time online table booking system allowing guests to select outlet, date,
     time slot, party size (1-8+), seating zone (indoor, outdoor, beachside), and
     special occasions/requests.
   - Instant booking confirmation with human-readable Booking IDs (e.g., BF-XXXX)
     and self-service reservation tracking/cancellation.
2. Manager Operations Dashboard (manager.html):
   - Control panel for restaurant floor managers and hosts.
   - Date, outlet, and status filtering (Confirmed, Seated, Completed, Cancelled, No-Show).
   - Real-time search across guests, IDs, phone numbers, and emails.
   - Interactive Visual Floor Map showing physical tables by zone, colored by live
     occupancy status (Available, Reserved, Occupied).
   - Walk-In Seating capability directly by clicking on available tables on the floor map.
   - One-click status transitions (Confirmed -> Seated -> Completed).
   - Real-time key metrics computation (Total active, Seated, Confirmed, Guests, No-Shows).
   - CSV export for daily operations and auditing.

Currently, the application runs entirely on client-side vanilla JavaScript and Vite,
using the browser's `localStorage` as a mock persistence layer. It is built to be
upgraded into a production-grade full-stack system.

4.7 Reservation Object Data Model (Stored in localStorage key 'bf_reservations')
--------------------------------------------------------------------------------
TypeScript-equivalent Interface:
interface Reservation {
  id: string;               // Prefix "BF-" + 4 random uppercase alphanumeric chars (e.g. "BF-8KD2")
  name: string;             // Customer full name
  email: string;            // Customer email address
  phone: string;            // Customer phone number (e.g. "+91 98765 12345")
  locationId: string;       // Outlet identifier (e.g. "anjuna")
  locationName: string;     // Formatted name (e.g. "Anjuna, North Goa")
  date: string;             // ISO date "YYYY-MM-DD"
  time: string;             // 24h format "HH:MM" (e.g. "19:30")
  guests: number;           // Party size integer (1 to 8+)
  seating: string;          // "any" | "indoor" | "outdoor" | "beachside"
  occasion: string;         // "" | "birthday" | "anniversary" | "date" | "business" | "other"
  notes: string;            // Free-form dietary/setup requests
  tableId: string;          // Assigned table (e.g. "ANJ-O3")
  tableType: string;        // "2-seater" | "4-seater" | "6-seater" | "8-seater" | "10-seater"
  tableZone: string;        // "indoor" | "outdoor" | "beachside"
  status: ReservationStatus;// 'confirmed' | 'seated' | 'completed' | 'cancelled' | 'no-show'
  createdAt: string;        // ISO 8601 timestamp
  seatedAt?: string;        // ISO timestamp populated when marked as 'seated'
  completedAt?: string;     // ISO timestamp populated when marked as 'completed'
  cancelledAt?: string;     // ISO timestamp populated when cancelled
  noShowAt?: string;        // ISO timestamp populated when marked as 'no-show'
}

type ReservationStatus = 'confirmed' | 'seated' | 'completed' | 'cancelled' | 'no-show';

5.2 src/js/booking.js (Booking Engine, Algorithms & Persistence)
--------------------------------------------------------------------------------
Dependencies: Imports `locationTables` and `locations` from `./data.js`.
Storage: Uses `localStorage.getItem('bf_reservations')` and `localStorage.setItem()`.

Internal Helper Functions:
- `generateBookingId()`: Returns formatted ID like 'BF-X7K9' picking 4 characters randomly from 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789' (avoids ambiguous characters 0/O, 1/I).
- `getReservations()`: Safely retrieves and JSON-parses reservations from localStorage. Returns empty array on JSON error.
- `saveReservations(reservations)`: Persists array of reservations to localStorage as JSON.
- `timeToMinutes(time)`: Converts "HH:MM" string to minutes from midnight (e.g., "13:30" -> 810).

Exported Functions:
- `formatTime(time24)`: Converts 24-hour "HH:MM" to 12-hour format with AM/PM (e.g., "13:30" -> "1:30 PM", "00:00" -> "12:00 AM").
- `formatDate(dateStr)`: Formats "YYYY-MM-DD" to Indian English locale string: "Weekday, Day Month Year" (e.g., "Friday, October 16, 2026").
- `getLocationName(locationId)`: Looks up location object by ID and returns "Name, Area" string.
- `checkAvailability(locationId, date, time, guests, seatingPref)`:
  The core table assignment & collision detection algorithm:
  1. Validates location existence in `locationTables`.
  2. Aggregates all tables across zones into `allTables` array, attaching `.zone`.
  3. Filters by `seatingPref` (supports zone alias fallbacks, e.g., 'outdoor' includes 'beachside').
  4. Filters tables having `capacity >= guestCount`.
  5. Sorts tables in ascending order of capacity (`a.capacity - b.capacity`) to achieve "Best Fit" (allocates smallest possible table to preserve large tables).
  6. Handles large groups (>6 guests) with specific advisory if no single table fits.
  7. Time Slot Collision Window: Assumes each reservation occupies a table for 90 minutes. Checks active bookings (excluding 'cancelled' status) on the same date, location, and tableId. If `|requestedTime - bookedTime| < 90`, collision occurs.
  8. Returns `{ available: true, table, message }` or `{ available: false, table: null, message }`.
- `createReservation(bookingData)`:
  Invokes `checkAvailability()`. If available, constructs complete Reservation record, generates ID, assigns table, marks status as 'confirmed', appends to storage, and returns `{ success: true, reservation }`.
- `createWalkInReservation(walkInData)`:
  Designed for Floor Managers on the manager dashboard:
  Takes `{ locationId, tableId, tableType, tableZone, guests, name, phone, notes }`.
  Calculates current live local date and current live time ("HH:MM").
  Constructs reservation with status 'seated', sets `seatedAt` timestamp, saves to storage, and returns `{ success: true, reservation }`.
- `lookupReservation(bookingId)`:
  Case-insensitive search in storage for a reservation matching the given booking ID.
- `cancelReservation(bookingId)`:
  Finds booking by ID, sets `status = 'cancelled'`, sets `cancelledAt` ISO timestamp, and saves. Returns boolean.
- `getAllReservations()`:
  Returns all reservation records (unfiltered).
- `updateReservationStatus(bookingId, status)`:
  Updates reservation status ('confirmed', 'seated', 'completed', 'no-show', 'cancelled').
  Automatically adds contextual ISO timestamps: `seatedAt`, `completedAt`, or `noShowAt`.
- `getLocationStats(locationId, date)`:
  Calculates total tables, total seat capacity, reservation count, total guests, and estimated occupancy rate for a specific location on a specific date.
- `seedDemoReservations()`:
  If localStorage is empty, automatically pre-populates 6 realistic reservations spanning today and tomorrow with diverse statuses ('confirmed', 'seated', 'completed') across Anjuna, Morjim, Panaji, and Delhi.

5.4 src/js/manager.js (Manager Operations Dashboard & Floor Map)
--------------------------------------------------------------------------------
Dependencies: Imports from `./data.js` and `./booking.js`.

State Management:
- `currentLocation` (default: 'all')
- `currentDate` (default: today's ISO date string)
- `currentStatus` (default: 'all')

Functions & Workflows:
- Auto-refresh: Automatically calls `refreshDashboard()` every 30 seconds (`setInterval`).
- `initDate()`: Syncs date input with today's date, updates human-readable header date display.
- `initFilters()`: Binds change listeners on location select dropdown and status filter pill buttons.
- `initSearch()`: Debounced live text search (300ms) matching guest name, booking ID, phone number, or email.
- `initActions()`: Manual "Refresh Data" and "Export Today's Data" CSV buttons.
- `refreshDashboard()`:
  - Fetches all reservations via `getAllReservations()`.
  - Filters by selected date, selected location, selected status filter, and live text search query.
  - Sorts reservations hierarchically: 'confirmed' first, then 'seated', 'completed', 'no-show', 'cancelled', and breaks ties by reservation time.
  - Calls `updateStats()`, `renderTable()`, and `renderFloorMap()`.
- `updateStats(reservations, date, location)`:
  Calculates dynamic counts for: Total Active, Confirmed, Currently Seated, Total Guests, Cancelled, and No-Shows. Uses `animateStatValue()` for smooth counting numbers.
- `renderTable(reservations)`:
  Renders responsive table rows with guest contact info, party size, table & zone, and contextual action buttons:
  - For Confirmed: "Seat" (sets status to 'seated'), "No-Show", "Cancel", and "Details".
  - For Seated: "Complete" (sets status to 'completed') and "Details".
- `renderFloorMap()`:
  - Renders physical table cards for the chosen outlet grouped by zones.
  - Compares each table's active reservations against current live time:
    - If status === 'seated' -> Marks table as "Occupied" (Blue).
    - If time slot overlaps now or upcoming today -> Marks table as "Reserved" (Amber).
    - Otherwise -> Marks table as "Available" (Green).
  - Clicking on a Reserved/Occupied table opens the detailed Reservation Modal.
  - Clicking on an Available table triggers `showWalkInModal()`!
- `showWalkInModal(table, zone)`:
  Opens modal allowing the restaurant host to seat walk-in guests on the fly:
  - Shows table capacity, selects guest count, optional phone and notes.
  - Clicking "Seat Guest Now" invokes `createWalkInReservation()`, immediately occupies the table on the floor map, and adds the record to reservations.
- `showReservationDetail(bookingId)`:
  Comprehensive modal showing all metadata: booking ID, status badge, guest details, party size, table, occasion, notes, and exact timestamps (`createdAt`, `seatedAt`, `completedAt`, `cancelledAt`).
- `exportData()`:
  Generates a clean CSV file (`burger-factory-reservations-YYYY-MM-DD.csv`) with full booking records and downloads it directly via a dynamically generated Blob URL.

8. END-TO-END USER WORKFLOWS & ALGORITHMIC LOGIC
================================================================================

8.1 Customer Booking Flow:
1. Customer enters landing page, browses menu, locations, or reviews.
2. Clicks "Book a Table" (smooth scrolls to `#booking`).
3. Fills in form (Name, Email, Phone, Outlet, Date, Time Slot, Party Size, Seating Preference, Occasion, Notes).
4. Submits form:
   - Client validates fields. If empty or email invalid, triggers visual error highlight and CSS shake animation.
   - `checkAvailability()` is executed:
     - Pulls all tables at chosen outlet.
     - Filters by seating preference (indoor, outdoor, beachside).
     - Filters by capacity >= party size.
     - Sorts ascending by capacity to pick optimal fit table.
     - Iterates through candidate tables; checks 90-minute time collision window against existing reservations in `localStorage`.
   - If no tables fit, displays warning toast: "Sorry, all suitable tables are booked...".
   - If available, constructs reservation with unique ID (e.g. "BF-3M9K"), writes to `localStorage`, and presents confirmation modal with copyable ID.

8.2 Customer Reservation Lookup & Cancellation Flow:
1. Guest scrolls to `#check-booking` section.
2. Enters Booking ID into `#check-booking-id` and clicks "Look Up".
3. System queries `lookupReservation(id)` from `localStorage`.
4. If found, displays formatted card showing status, name, location, date, time, and assigned table.
5. If status is 'confirmed', renders "Cancel This Reservation" button.
6. Clicking cancel triggers confirmation prompt, updates status to 'cancelled' with ISO timestamp, and immediately refreshes display and stats.

8.3 Manager Operations & Status Mutation Flow:
1. Manager visits `/manager.html`.
2. Dashboard auto-loads today's date, initializes stats counters, reservations table, and visual floor map.
3. Manager can filter by location (e.g., Anjuna) to see outlet-specific data.
4. When guest arrives: Manager clicks "Seat" button -> Reservation status changes to 'seated', `seatedAt` timestamp recorded, floor map turns table Blue (Occupied).
5. When dining finishes: Manager clicks "Complete" -> Reservation marked 'completed', table on floor map turns Green (Available).
6. If guest does not arrive: Manager clicks "No-Show" -> Status marked 'no-show', table freed.
7. Background timer re-syncs dashboard every 30 seconds.

8.4 Walk-In Floor Plan Seating Flow:
1. Manager views the Visual Table Floor Map on `/manager.html`.
2. Available tables appear green with their ID, type, and zone.
3. Manager clicks an available table card -> triggers `showWalkInModal(table, zone)`.
4. Modal opens with guest count options up to table capacity, optional name/phone.
5. Manager clicks "Seat Guest Now" -> invokes `createWalkInReservation()`, creates record with status 'seated', and immediately turns the table blue on the map.

8.5 CSV Reporting & Analytics Export:
1. Manager clicks "Export Today's Data" button.
2. System extracts filtered reservations for current date and location.
3. Serializes records into RFC-compliant CSV format with escaped double quotes.
4. Creates a downloadable Blob and triggers download: `burger-factory-reservations-YYYY-MM-DD.csv`.

9. CURRENT TECHNICAL DEBT, LIMITATIONS & ARCHITECTURAL GAPS
================================================================================
While the frontend UI, design system, and client logic are fully functional and
feature-complete, the following architectural gaps exist for a production rollout:

1. Persistence & State Storage:
   - CURRENT: Uses browser `localStorage` (`bf_reservations`).
   - GAP: Data is isolated to a single browser. If a customer books from their phone,
     the manager cannot see it on their laptop! No database exists.
2. Authentication & Authorization:
   - CURRENT: Anyone who navigates to `/manager.html` has full access to view, edit,
     and cancel all bookings.
   - GAP: No authentication (JWT / session cookies), no role-based access control
     (Host, Floor Manager, Admin, Owner).
3. Backend Server & API Layer:
   - CURRENT: Static client-only application bundled by Vite.
   - GAP: No Node.js / Python / Go REST or GraphQL API backend; no server-side
     validation; no connection pooling.
4. Concurrency & Race Conditions:
   - CURRENT: Two customers booking the same table simultaneously in different browsers
     will both succeed locally because there is no centralized database transaction lock.
   - GAP: Need ACID transactions, row-level locking, or Redis distributed locks.
5. Real-Time Synchronization:
   - CURRENT: 30-second client-side polling interval (`setInterval`).
   - GAP: No WebSockets or Server-Sent Events (SSE) to push instant table status
     changes to the floor manager in real-time.
6. Notifications & Communications:
   - CURRENT: Toast message saying "SMS/Email reminder" will be sent, but no external
     communication service is connected.
   - GAP: Need Twilio / WhatsApp Business API / SendGrid integration for automated
     booking confirmation and reminder messages.
7. Online Payments / Booking Deposits:
   - CURRENT: Reservations are free with no deposit required.
   - GAP: For large groups (e.g. 6-8+ guests), restaurants usually require a table
     holding deposit via Razorpay or Stripe to prevent no-shows.
8. Menu Management:
   - CURRENT: Menu items, prices, and locations are hardcoded in `src/js/data.js`.
   - GAP: Manager cannot mark an item as "86'd" (sold out), change prices, or add
     daily specials without modifying source code.
