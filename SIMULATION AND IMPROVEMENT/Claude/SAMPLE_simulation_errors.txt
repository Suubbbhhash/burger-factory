[CRITICAL] DOUBLE_BOOKING - 7 occurrence(s), first at D01 Sat 23:59
  Likely cause : Availability is checked in the browser, then the result is POSTed. Two phones can both see the same table as free. The dev server (vite.config.js, POST /api/v1/reservations) appends whatever it receives; in production the findFirst-then-create in reservation.routes.ts runs at READ COMMITTED so two transactions can still both pass, and schema.prisma enables btree_gist but never declares the exclusion constraint.
  Where to look: vite.config.js POST handler; src/js/booking.js createReservation(); apps/api/src/modules/reservations/reservation.routes.ts ($transaction); prisma schema/migrations
  Suggested fix: Let the SERVER choose the table inside a lock/transaction. In Postgres add: ALTER TABLE reservations ADD CONSTRAINT no_table_overlap EXCLUDE USING gist (table_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (status IN ('CONFIRMED','SEATED')); catch SQLSTATE 23P01 and retry the next candidate table. In the dev server add an async mutex and re-run checkAvailability() before pushing. Disable the Confirm button after first tap and send an idempotency key.
[CRITICAL] GHOST_CONFIRMATION - 4 occurrence(s), first at D01 Sat 23:59
  Likely cause : The client wraps every fetch in try { ... } catch {} and shows success regardless, so a dropped/failed request still produces a confirmation screen and a booking code that the restaurant never received.
  Where to look: src/js/booking.js createReservation / createWalkInReservation / cancelReservation / updateReservationStatus (all "catch {}")
  Suggested fix: Show the confirmation only after a 201 from the server; on failure show an error + retry; keep an outbox with retry/backoff for the host tablet; never write to localStorage before the server acknowledges.
[CRITICAL] SERVER_NO_CONFLICT_CHECK - 1 occurrence(s), first at D01 Sat 13:33
  Likely cause : The server trusts the client completely and never validates overlap.
  Where to look: vite.config.js POST /api/v1/reservations
  Suggested fix: Move checkAvailability() into the server handler and return 409 on conflict; client should re-fetch and offer another slot.
[CRITICAL] SECURITY_NO_AUTH - 1 occurrence(s), first at D01 Sat 13:33
  Likely cause : Mutation endpoints have no authentication. The passcode "burger123" is in client JS; phone-last-4 verification is performed in the browser only. In the Fastify API only /auth/me calls jwtVerify; floor routes (/walkin, status PATCH, /events, /manifest) have no preHandler.
  Where to look: vite.config.js; apps/api/src/modules/floor/floor.routes.ts; src/js/manager.js passcode gate
  Suggested fix: Add a Fastify preHandler (request.jwtVerify + role check) to the floor plugin; verify phoneLast4 server-side for guest cancel/lookup (already done in /reservations/cancel); remove hard-coded passcodes from shipped JS.
[CRITICAL] SECURITY_PII_EXPOSURE - 1 occurrence(s), first at D01 Sat 13:33

  Where to look: vite.config.js GET handler; booking.js syncReservationsFromServer
  Suggested fix: Expose only an /availability endpoint (anonymous) and a staff-only list; never ship other guests' PII to a customer browser.
