# Full pipeline for building a fast, scalable website

I'm assuming a typical dynamic site (users, data, maybe a cart or forms). The stack is a suggestion; the principles apply to any stack.

## Phase 0: Plan before you code

- **Define the core user flows** (browse → search → action → confirm). Everything else is secondary.
- **Wireframe first** (Figma or even paper): pages, navigation, states (empty, loading, error).
- **Design tokens**: pick colors, 1-2 fonts, a spacing scale (4/8px), radii, and shadows up front. This is 80% of "looks amazing."
- **Estimate load**: if 1000 concurrent users each make about 1 request/sec, that's about 1000 req/s. Design for 5-10x that.
- **Define the data model** (ERD) before writing endpoints.

## Phase 1: Architecture

```
Browser
  → CDN / static cache
  → Reverse proxy + load balancer (Nginx)
  → App servers (N stateless instances)
  → Cache (Redis)  ← read-heavy data
  → Database (Postgres) + read replicas
  → Queue/workers (emails, image processing, heavy jobs)
```

Key rule: **make app servers stateless** (no sessions or files stored in server memory or on disk). Then you can run 1 or 20 copies behind a load balancer and nothing breaks.

Start with a **modular monolith**, not microservices. It's simpler, faster, and scales to far more than you'd expect. Split later only if needed.

## Phase 2: Project structure

```
project/
├── apps/
│   ├── web/                  # frontend
│   │   ├── src/
│   │   │   ├── components/   # reusable UI (Button, Card, Modal)
│   │   │   ├── features/     # feature-based (cart/, auth/, products/)
│   │   │   ├── pages|routes/
│   │   │   ├── hooks/
│   │   │   ├── lib/          # api client, utils
│   │   │   ├── styles/       # tokens, globals
│   │   │   └── assets/
│   │   └── public/
│   └── api/                  # backend
│       ├── src/
│       │   ├── modules/      # users/, products/, orders/ (each: routes, controller, service, repo, schema)
│       │   ├── middleware/   # auth, rate-limit, validation, error handler
│       │   ├── db/           # migrations, seeds, connection
│       │   ├── jobs/         # queue workers
│       │   ├── config/       # env parsing
│       │   └── server.ts
├── infra/                    # nginx.conf, docker-compose.yml, k6 scripts
├── .env.example
└── README.md
```

Organize by feature, not by file type, so related code lives together.

## Phase 3: Frontend

**Stack suggestion**: Next.js (React) or SvelteKit, TypeScript, Tailwind or CSS modules.

**Looks**
- Consistent design system: build components once, reuse everywhere.
- Generous whitespace, strong typographic hierarchy, one accent color.
- Subtle motion (150-250ms transitions, Framer Motion or CSS); no gratuitous animation.
- Dark mode via CSS variables.
- Skeleton loaders instead of spinners; real empty and error states.
- Mobile-first and responsive (flexbox/grid, `clamp()` for fluid type).
- Accessibility: semantic HTML, contrast, keyboard nav, focus states, alt text.

**Performance**
- Server-side rendering or static generation for public pages; client rendering only for interactive parts.
- Code-split by route and lazy-load heavy components.
- Images: WebP/AVIF, responsive `srcset`, lazy loading, explicit width/height (prevents layout shift).
- Fonts: self-host, subset, `font-display: swap`.
- Keep the JS bundle small (audit with a bundle analyzer, avoid heavy libs).
- Cache API data client-side (TanStack Query / SWR) with debouncing on search inputs.
- Target Core Web Vitals: LCP < 2.5s, CLS < 0.1, INP < 200ms (measure with Lighthouse).

## Phase 4: Backend

**Stack suggestion**: Node (Fastify/NestJS) or Python (FastAPI) or Go. Any works if you follow these rules.

- **REST (or GraphQL) with versioning** (`/api/v1/...`), consistent JSON shape, proper status codes.
- **Validate every input** (Zod/Pydantic) at the edge.
- **Auth**: short-lived access tokens plus refresh tokens in httpOnly cookies; hash passwords with argon2/bcrypt; role-based access.
- **Pagination everywhere** (cursor-based for big lists). Never return unbounded results.
- **Idempotency keys** on payments/orders so retries don't double-charge.
- **Centralized error handling and structured logging** (JSON logs with request IDs).
- **Background jobs** (BullMQ/Celery) for anything slow: emails, PDFs, image resizing. The request returns immediately.
- **Timeouts on every external call**, plus retries with backoff and circuit breakers.
- **Graceful shutdown** and health endpoints (`/health`, `/ready`).

## Phase 5: Database (usually the first bottleneck)

- **Postgres** is a safe default.
- **Index** columns you filter, join, and sort on; check queries with `EXPLAIN ANALYZE`.
- Avoid N+1 queries (batch or join).
- **Connection pooling** (PgBouncer or your driver's pool). Thousands of users must not mean thousands of DB connections.
- **Migrations** under version control.
- Scale path: add indexes → cache → read replicas → partitioning, in that order.
- Store files/images in object storage (S3-style), not in the DB.

## Phase 6: Caching (biggest win per effort)

Layers, outermost first:
1. **Browser cache**: `Cache-Control`, ETags, immutable hashed assets.
2. **CDN**: static assets and cacheable pages.
3. **Redis**: hot queries, sessions, rate-limit counters, computed results with TTLs.
4. **In-process cache**: tiny, very hot lookups.

Plan invalidation (TTL, or purge on write) and guard against **cache stampede** (locking or stale-while-revalidate).

## Phase 7: Networking

- **Nginx/Caddy reverse proxy**: TLS termination, gzip/Brotli compression, static file serving, buffering.
- **Load balancing** across app instances (round-robin or least-connections) with health checks.
- **HTTP/2 or HTTP/3** for multiplexing.
- **Keep-alive connections** between proxy and app.
- **Rate limiting** per IP/user (Nginx plus app-level with Redis) to survive abuse and traffic spikes.
- **Request size limits and timeouts** to block slowloris-style attacks.
- **CORS** locked to known origins; security headers (CSP, HSTS, X-Content-Type-Options).
- **WebSockets/SSE** (if needed) via a pub/sub layer (Redis) so multiple instances can broadcast.
- **Graceful degradation**: if a non-critical service (recommendations, analytics) fails, the page still works.

## Phase 8: Making it "not crash at 1000s of users"

No site is crash-proof, but you can make failure rare and gentle:
- Stateless horizontal scaling, with queues absorbing spikes.
- Caching so most requests never hit the DB.
- Rate limits and **backpressure** (return 429/503 early rather than melting).
- Async I/O and no blocking calls on the main thread.
- Memory discipline: stream big responses and avoid loading huge datasets into memory.
- Auto-restart (Docker restart policy/PM2/systemd).

## Phase 9: Test it locally without going public

- **Docker Compose** the whole stack: Nginx, 2-3 app containers, Postgres, Redis. That simulates production on your laptop.
- **Load test with k6, Locust, or autocannon**: ramp from 100 to 1000+ virtual users and watch p95/p99 latency, error rate, CPU, memory, and DB connections.
- Find the bottleneck, fix it, re-run. Repeat.
- **Testing pyramid**: unit tests (logic), integration tests (API plus DB), a few end-to-end tests (Playwright) for critical flows.
- **Lighthouse and WebPageTest** for frontend performance.
- **Security basics**: OWASP Top 10 checklist, dependency audit (`npm audit`), SQL injection and XSS checks.

## Phase 10: Observability and workflow

- Logging, metrics (Prometheus/Grafana), error tracking (Sentry), and tracing (OpenTelemetry) so you can see what breaks.
- Git with feature branches, linting and formatting (ESLint/Prettier), pre-commit hooks, and CI running tests on every push.
- Config via environment variables; never commit secrets.

## Suggested build order

1. Wireframes and design tokens
2. Data model and DB schema
3. Backend skeleton (auth, one core module) with validation and error handling
4. Frontend shell and component library
5. Connect the core flow end to end
6. Add remaining features
7. Add caching, queues, and rate limiting
8. Dockerize and put Nginx in front
9. Load test, profile, optimize
10. Security pass, then polish animations and accessibility
